****# `dj deploy` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `dj deploy status|now|log` runs a project's deploy command on its server over SSH. The first run asks for the server and checks it, and an agent skill tells coding agents how to use the command.

**Architecture:** `dj` holds no deploy logic. It saves a `{host, command}` pair per repo in `~/.dj/config.json` (next to the existing `~/.dj/skills`), keyed by the normalized `origin` URL. Each subcommand becomes `ssh <host> <command> <subcommand>`. Setup is interactive with `@inquirer/prompts` (already a dependency), takes flags when there's no TTY, and checks the target over SSH before saving.

**Tech Stack:** TypeScript, commander 12, `@inquirer/prompts` 7, chalk 5, vitest 2. Tests mock `child_process` and `@inquirer/prompts`, as `tests/tidy.test.ts` does.

**Spec:** No separate spec file. The design was agreed in chat on 2026-10-21. The server half is `bt-assistant/docs/superpowers/plans/2026-10-21-auto-deploy-server.md`, which defines the remote `bt-deploy status|now|log` command this wraps.

## Global Constraints

- Branch: `feat/deploy`, cut from `main` (not from the current `feat/tidy-worktrees`).
- No new dependencies.
- Config file: `path.join(home, ".dj", "config.json")`. Create `~/.dj` if it's missing. Shape: `{ "deploy": { "<repoKey>": { "host": string, "command": string } } }`. Keep any other top-level keys untouched when writing.
- Don't mutate config objects. Writing returns a new object, then serializes it with 2-space indentation and a trailing newline.
- The SSH check is exactly `ssh -o BatchMode=yes -o ConnectTimeout=10 <host> <command> status`.
- Default command: `bt-deploy`.
- User-facing copy, word for word:
  - No TTY and no target: `No deploy target for <repoKey>. Run: dj deploy setup --host <ssh-host> --command <remote-command>`
  - Exit 255: `Can't reach <host> over SSH. Check that "ssh <host>" works.`
  - Exit 127: `<host> has no "<command>". Enable its deploy module on the server.`
  - Saved: `Saved. Change it later with: dj deploy setup`
- Commit messages follow `<type>: <description>`.

## Review Focus

1. **The host or command could inject options or shell code.** `ssh` passes the remote command to a shell, and a host starting with `-` becomes an ssh option. Validate before saving and before every use. Host: `/^[A-Za-z0-9][A-Za-z0-9._@:-]*$/`. Command: `/^[A-Za-z0-9_./-]+$/`. Tests are in Task 1.
2. **`~/.ssh/config` is missing or has no hosts.** The owner's Mac lists only `piclustermaster`, and reaches the server as `nixos` through Tailscale DNS. With no hosts, skip the picker and go straight to a text input, and always offer "Other…" when there is a list. Tests are in Task 2.
3. **The config file is corrupt or hand-edited.** Fail with the file path and `Fix or delete it`, and never overwrite it silently. Test is in Task 1.
4. **Not in a git repo, or no `origin` remote.** Fail with `dj deploy needs a git repo with an "origin" remote.` Test is in Task 1.
5. **`dj deploy now` streams through `ssh -t` only when stdout is a TTY.** Agents and pipes get plain `ssh`, so no pseudo-terminal warnings and the exit code passes through. Test is in Task 3.

### Task 2: `dj deploy setup`

**Files:**
- Create: `src/commands/deploy/setup.ts`
- Test: `tests/deploy-setup.test.ts`

**Interfaces:**
- Consumes: everything Task 1 produces.
- Produces:
  - `sshHosts(sshConfig: string): string[]` lists the names on `Host` lines (several per line allowed, matched case-insensitively), drops any containing `*`, `?` or starting with `!`, and removes duplicates in order.
  - `checkTarget(t: DeployTarget): { ok: true } | { ok: false; message: string }` runs the SSH check with `spawnSync` and `stdio: ["ignore", "ignore", "pipe"]`. 0 → ok, 255 → unreachable copy, 127 → missing-command copy, anything else → `<command> status failed on <host>: <first stderr line>`.
  - `setupTarget(opts: { host?: string; command?: string; interactive: boolean; home: string; key: string }): Promise<DeployTarget>` asks for whatever wasn't passed (only when `interactive`), validates, checks, saves, prints the saved message, and returns the target. A failed check throws its message and saves nothing.

- [ ] **Step 1: Write the failing tests**

Mock `child_process` (`spawnSync`, `execFileSync`) and `@inquirer/prompts` (`select`, `input`). Cases:
- `sshHosts("Host a b\n  HostName x\nHost *\nhost c\nHost !d\nHost a\n")` → `["a", "b", "c"]`
- `checkTarget` maps status 0 / 255 / 127 / 1 (stderr `boom\nmore`) to ok, the two exact copy lines, and `bt-deploy status failed on nixos: boom`, and calls `spawnSync("ssh", ["-o","BatchMode=yes","-o","ConnectTimeout=10","nixos","bt-deploy","status"], …)`
- with `--host nixos` and no `--command`, not interactive: saves `{host:"nixos",command:"bt-deploy"}` and never prompts
- no host, not interactive: throws the exact "No deploy target" copy with the key filled in
- interactive with an empty host list: calls `input` for the host (never `select`), then `input` for the command with default `bt-deploy`
- interactive with hosts `["piclustermaster"]`: `select` offers `piclustermaster` and `Other…`, and choosing `Other…` leads to `input`
- interactive with existing saved target: the saved values are the prompt defaults
- a failed check throws and leaves the config file unchanged

- [ ] **Step 3: Write the skill.** Follow the shape and tone of `skills/dj-init/SKILL.md`. Run the `humanizer:humanizer` skill on the text. It must say:
  - **Description (frontmatter):** use when the user asks whether a merge is live, which commit the server runs or is testing, when the last deploy check ran, or to deploy now.
  - **Read before acting:** `dj deploy status` is read-only and safe to run anytime. `dj deploy log` is read-only too.
  - **`dj deploy now` changes production.** Run it only when the user asks to deploy, and show the command first. It can take several minutes (install plus tests plus restart). Let it finish, and never interrupt it.
  - **Setup:** agents have no TTY, so `dj` never prompts them. If you see the "No deploy target" message, ask the user for the SSH host, then run `dj deploy setup --host <host> --command bt-deploy`. Never guess a host.
  - **Reading `status`:** `running` different from `live` means a restart failed. `testing` other than `idle` means a check is in progress. A commit under `last failed` won't be retried; a new commit on `main` is needed.
  - **Errors:** report the exact line `dj` printed (unreachable host, missing command) and stop. Don't try `ssh` options or `sudo` on the server.
  - **Never** edit `~/.dj/config.json` by hand, or run commands on the server outside `dj deploy`.
